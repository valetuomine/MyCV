# Frontend Integration Patterns

## Route and data loading

- Keep components rendered directly by React Router in feature-local `routes` folders (for example, `pages/Profile/components/routes`, `pages/Admin/routes`, and `auth/routes`). Keep reusable UI and route helpers with their feature components, outside the route folders.
- Keep frontend route patterns and navigation destinations in `src/routePaths.ts` as the `RoutePaths` object. Use PascalCase members (for example, `RoutePaths.Home`) for fixed routes and path builders rather than repeating path strings in route registration, navigation, or authentication redirects. Keep API endpoint URLs with their RTK Query endpoints.
- Use React Router for browser navigation. Public Candidate profiles use one route parameter only: `/:publicUrlSegment`; do not append `/profile`.
- The Static Web Apps deployment must provide SPA navigation fallback to `/index.html` so a deep link such as `/<publicUrlSegment>` loads the React app.
- Fetch server state with RTK Query (`createApi`/`fetchBaseQuery`) and generated hooks. Do not create ad-hoc `fetch` effects for endpoint-backed resources or duplicate the same data in Jotai.
- Keep RTK Query endpoint definitions in resource-specific files: `src/api/candidateQueries.ts` for Candidate operations and `src/api/profileQueries.ts` for Profile operations. Profile queries include public and admin reads; Profile POST/PUT are mutations. Share the `baseApi` instance so the store registers one reducer and middleware.
- Load `GET /api/Candidate/{publicUrlSegment}` first. Use its `profileId` to conditionally load `GET /api/Profile/{profileId}`. Handle loading, errors, unknown candidates, and candidates without a profile explicitly.
- Binary responses such as the Profile PDF (`GET /api/Profile/{profileId}/pdf`) are not RTK Query data: build their URL with a helper next to the resource's endpoints (`getProfilePdfUrl` in `profileQueries.ts`) and let the browser load it in an `<object>` or a link. The API serves it `inline`, and `download=true` switches it to `attachment`, because the `download` attribute is ignored on cross-origin links. The profile picture is the same: `getProfilePictureUrl` prefixes the DTO's relative `pictureUrl` with `VITE_API_BASE_URL` for an `<img>`. Its changes are RTK Query mutations that send `FormData` (`saveProfilePicture`) or no body, and invalidate the profile's `Profile` tag, which refetches the CV and the edit view without resetting the edit form, because the form's values don't include the picture.
- The API does not lay PDFs out. It prints a frontend print route in headless Chromium with Playwright (`HtmlPdfPrinter` in `CV.Logic/Pdf`). A print route such as `/print/:profileId?lang=fi|en` (`ProfilePrintRoute`) is declared outside the `Background` layout route in `App.tsx`, takes its language from the URL rather than `languageAtom`, forces the light theme, sets `data-print` on `<html>` for white paper, and puts per-page footers in `@page` margin boxes. It must set `data-print-ready` once its data and `document.fonts.ready` are in, or `data-print-error` when loading fails, because the printer waits for one of them. Reserve the route's first segment as a CV link in both `ProfileService` and `profile-form-schema.ts`.
- Keep local/shared UI state in Jotai atoms where it is used across components; do not put server response caches in Jotai.
- Wrap the app with Redux Toolkit's `<Provider>`, Jotai's `<Provider>`, and `<BrowserRouter>` in the entry point. Register the RTK Query reducer and middleware in the Redux store.

## Sign-in and sign-out

- Two sign-in methods share one session: Microsoft through MSAL (`src/auth/entraAuth.ts`) and Google directly through OpenID Connect (`src/auth/googleAuth.ts`, an ID token from `response_type=id_token` with a nonce; no client secret). Read the signed-in state with `useAuthSession()` (`src/auth/authSession.ts`), which combines `useMsal()` and the Google session store; never call `useMsal()` in routes or components. Only one method is active at a time: `startSignInRedirect` clears the other method's session before redirecting. The `SignInMethod` const lives in `src/types.ts`.
- Start sign-in with `useLoginRedirect` from the route that needs it, and set its `redirectPath` (MSAL's `redirectStartPage`) to that same route, for example `RoutePaths.CandidateAdmin(publicUrlSegment)` rather than the public profile. It doesn't redirect by itself: `SignInMessage` shows a choice of the configured methods (`SignInMethodButton`, in the providers' brand colours from the `--cv-google-*` and `--cv-microsoft-*` tokens), and the chosen method's `startSignIn(method)` runs the hold and the redirect. Retry reuses the method that failed. MSAL completes a redirect on the start page, so a cancelled or failed Microsoft sign-in lands back on the screen that can explain it and offer a retry. Once an account exists, that route forwards to its destination with `<Navigate replace>`. `src/auth/entraAuth.ts` sets the active account on `LOGIN_SUCCESS`, so routes never call `setActiveAccount` themselves.
- Google returns to `RoutePaths.GoogleAuthCallback` (`/auth/callback/google`) with the ID token in the URL fragment. `googleAuth.ts` captures and removes the fragment when the module loads, before React renders, because MSAL reads the fragment on every page load and the callback route loads lazily. `GoogleAuthCallbackRoute` calls `completeGoogleSignIn()` (once per page load), which checks `state`, `nonce`, `aud`, `iss` and `exp` and stores the session in session storage, never local storage; the API verifies the signature. Both callback routes render `SignInCallback`, which sends the user on from the return markers and shows failures naming the provider; its Try again opens the sign-in route with `retrySignInLocationState(method)`, so `useLoginRedirect` starts that method again at once.
- Remember the method of the last successful sign-in with `storeLastSignInMethod` (`adminLoginStorage.ts`, local storage under `lastSignInMethodKey`, wrapped in try/catch) and show it as the "Last used" badge. `entraAuth.ts` stores it on `LOGIN_SUCCESS`, `googleAuth.ts` after a valid Google response.
- MSAL reports redirect failures only through its event stream. `src/auth/entraAuth.ts` records `ACQUIRE_TOKEN_FAILURE` events for redirect interactions in a small store; read it with `useSyncExternalStore(subscribeRedirectSignInError, getRedirectSignInError)`. While a failure is recorded, never start another redirect automatically; wait for the user's retry, otherwise a cancel loops straight back to Microsoft. Use `isSignInCancelled` to tell a cancel (`user_cancelled`, `access_denied`) from a real error. Call `clearRedirectSignInError()` on retry and when the screen that showed the failure unmounts.
- Treat auth return-path session-storage values in `src/auth/adminLoginStorage.ts` as one-shot navigation markers, not authentication or database state. Clear them all with `clearAuthReturnPaths()` after reading in the callback, on redirect failure, at the authenticated destination once MSAL is idle, and when abandoning the flow for Home. When a value must survive the clearing effect, read it during render in a `useState` initializer.
- Sign out with `signOutInApp` (`src/auth/authSession.ts`), never `logoutRedirect`, so neither provider's logout page shows. It records the `SignOutReason` in a small store first (read it with `useSigningOutReason`, which `Background` uses to show the sign-out screen), clears MSAL's cache with `clearCache()` and the Google session with `clearGoogleSession()`, stores the return markers with `storeSignOutReturn`, waits `signOutHoldMs` (3.5 seconds, like the sign-in's `redirectHoldMs`) so the sign-out screen doesn't just flash, and reloads Home with `window.location.replace`; the reload also drops open editors and cached admin data. Keep the hold after the cache clearing and the markers, so a tab closed during it is still fully signed out. If `clearCache()` fails, it resets the store and rethrows, which leaves the user signed in on the page they were on. Sign-out must return to a public route rather than the protected route that would immediately start sign-in again: the markers hold the current profile's `publicUrlSegment` under `logoutReturnPublicUrlSegmentKey`, or `""` when there is none (for example on `/admin`), and the `SignOutReason` (`User` from `SignOutButton`, `Idle` from `useIdleSignOut`) under `signOutReasonKey`. Home then forwards to that public profile with `<Navigate replace>`, or stays on Home for `""`. Both pass `signedOutLocationState(reason)` (`src/auth/signedOutState.ts`) so `SignedOutNotice` can confirm the sign-out with the reason's message; the notice then replaces the router state so a reload does not replay it.
- Because the provider sessions outlive an in-app sign-out, `storeSignOutReturn` also sets `signInPromptRequiredKey` in local storage, so it reaches new tabs. While it is set, `startSignInRedirect` passes `prompt: PromptValue.LOGIN` to Microsoft and `prompt=select_account` to Google, and a successful sign-in with either method clears it. Google has no `prompt=login` and ignores `max_age=0` (tested in US-58), so after an in-app sign-out it shows only the account chooser, without the password: the in-app sign-out never ends the Google session itself. Every sign-out must go through `storeSignOutReturn`, or the next sign-in skips the credential prompt.
- `useIdleSignOut`, called once in `Background`, signs the user out after 5 minutes without pointer, key, wheel, scroll or touch input. It measures time since the last activity and checks it on an interval, on `visibilitychange` and on the next input, rather than with one long timer, because hidden tabs throttle timers and sleeping devices pause them.

## API base URL and types

- Use `VITE_API_BASE_URL` as public build-time configuration for the deployed API origin. It is not a secret. Leave it empty locally to use the Vite `/api` development proxy.
- Never place API keys, tokens, passwords, or other credentials in `VITE_*` variables.
- Derive API response types from `src/generated/openapi.ts`. After changing API DTOs or routes, regenerate OpenAPI types from the running Development API using the frontend's `generate-types` script; do not hand-edit the generated file. `.claude/settings.json` blocks reading it to save tokens: its schema names are the backend DTO and request class names under `src/Backend/CV.LogicInterface/Dto/` (for example `components["schemas"]["ProfileDto"]`), so read the class there instead.
- Add frontend dependencies only when absent; reuse the existing React Router, Redux Toolkit/RTK Query, Jotai, and React Redux packages.

## Form component conventions

- Define a named props interface for form-related components instead of using an inline object type in the component signature.
- Use descriptive prop names that match the value's role (for example, `values: Profile` for form data), while keeping the appropriate domain type.
- When create and update forms share fields, extract only the common field rendering into a reusable component. Keep `useForm`, create-only `defaultValues`, authentication, API mutations, submit/cancel actions, and mutation status in the owning route or form controller.
- Keep create-only fields such as `publicUrlSegment` outside the shared Profile fields. Use the base `ProfileSchema` for common field names and extend it with `CreateProfileSchema` for create-only data.
- Keep typed create-form defaults beside the matching Zod schema and pass them to `useForm` from the route. Initialize required nested collections (such as Finnish and English translation rows); do not embed defaults or submission behavior in shared field-rendering components.
- In form controllers, destructure the React Hook Form methods used by the component (for example, `handleSubmit` and `reset`) from the `useForm` result instead of repeatedly accessing them through the form object. Use `useWatch` for field subscriptions in React Compiler components; calling `form.watch()` triggers the compiler's `incompatible-library` warning and skips compilation. Only destructure `reset` when the controller has a reset flow, such as cancelling edits.
- For edit forms hydrated from RTK Query, map the API result to the form shape and pass it through React Hook Form's `values` option so asynchronously loaded data populates the form; reset to the same mapped values when cancelling edits. Reserve `defaultValues` for fixed initial state such as a blank create form.

## Admin mutation safety

Define Profile POST and PUT as RTK Query mutations in `profileQueries.ts`, with OpenAPI request/response types; invalidate the matching Profile query after a successful PUT.

Profile POST requires authentication, and the API links the caller's validated sign-in identity (Entra `tid`/`oid`, or Google `sub`) to the new candidate as its first login. It answers `403` when a Google account isn't on the sign-up list and `409` when the sign-in already has a CV; `getProfileFormError` turns both into their own messages. Profile update/delete/admin-read and Candidate delete are permitted to a caller with one of the candidate's logins or the global `CvAdmin` role, which only Microsoft sign-in carries; the API is the authorization boundary. The frontend may query the admin Profile endpoint to determine whether to show editing controls, but must not treat that result as security enforcement. The frontend attaches `acquireApiToken()` (`src/auth/authSession.ts`) to RTK Query requests: the MSAL access token for the delegated `access_as_user` scope, or the Google ID token while it is valid for at least another 60 seconds. On an interaction-required MSAL error, it redirects through Entra and returns to the current route. When the Google token has expired, it starts one silent redirect to Google (`prompt=none`, `login_hint=<sub>`) that returns to the current page; when that fails, the session is cleared and the user lands on the page's sign-in route. Google configuration (`VITE_GOOGLE_CLIENT_ID`, the Google button hides without it) is kept out of the repository like the Entra values. Entra client configuration, the API audience, and tenant MFA setup are kept out of the repository, which is public. When creating a Profile, use the returned `publicUrlSegment` for the public route; `candidateId` remains an internal identifier and is never the public URL.
