# Candidate/Profile Relationships

These rules are specific to the CV application and should not be generalized to unrelated resources.

## Candidate ownership

Candidate is the relationship owner. `Candidate.Id` is the stable internal GUID. `Candidate.PublicUrlSegment` is the unique public CV URL segment and API lookup key. `Profile.Id` is a separate internal identifier used to retrieve profile content. `Candidate.Logins` (`CandidateLogin` rows) are the sign-in identities that own the Candidate. Each login stores the provider (`LoginProvider.Entra` or `LoginProvider.Google`), its tenant or issuer (Entra `tid`, or `https://accounts.google.com`) and the user ID (Entra `oid`, or Google `sub`). A unique index on those three columns keeps one identity on one Candidate. Never use the email address as an identity key, and never log these IDs or return them from the API.

Deleting a Candidate must delete every related row using IDs stored on Candidate, such as `ProfileId` and future `WorkHistoryId` values. Keep this cascade behavior in `CvContext.CascadeDeleteCandidateReferences` so every Candidate deletion follows the same rule.

## Profile deletion

Deleting a Profile must not delete Candidate. The Profile service must:

1. Find the Candidate whose `ProfileId` points to the profile.
2. Set that `ProfileId` to `null`.
3. Remove only the Profile.
4. Save both changes together.
5. Delete the profile's picture blob, if it has one, through `IProfilePictureStore.RemoveUnused` after the save.

Deleting a Candidate deletes its Profile through `CascadeDeleteCandidateReferences`, which knows only the profile's ID, so `CandidateService` reads the profile's `PictureBlobName` before the save and deletes that blob after it.

## Profile pictures

- `Profile.PictureBlobName` names the picture's blob, `{profileId}/{guid}.webp` (`ProfilePictureNames`), in the private `profile-pictures` container. Every picture gets a new name, so a stored blob never changes. A picture change updates the column only while it still holds the name the request read (`ExecuteUpdate` with that condition); otherwise the change answers 409 and deletes its own new blob, so two changes at the same time can't leave a blob unused. Its `guid` is the version in `ProfileDto.PictureUrl` and `ProfileAdminDto.PictureUrl` (`/api/Profile/{profileId}/picture?v={guid}`, relative to the API's origin and the same in every language), and the GET endpoint caches the current version for good.
- `ProfilePictureService` owns the picture: upload (`PUT .../picture`, multipart field `file`, at most 10 MB), the Google picture (`PUT .../picture/google`, from the caller's Google token's `picture` claim, checked by `GooglePictureUri`: only on `googleusercontent.com` over `https`, never a URL from the request), delete (`DELETE .../picture`) and the public read (`GET .../picture`). The writes follow the owner-or-`CvAdmin` rule, with 404 for a non-owner, set `Profile.UpdatedAt` (so the CV's date and the PDF cache key change), and are saved at once, apart from `UpdateProfile`.
- `ProfilePictureProcessor` checks the format from the file's bytes (JPEG, PNG or WebP), refuses too many pixels from the header before decoding, turns the image upright by its EXIF orientation, scales it to at most 1200 px and re-encodes it as WebP with SkiaSharp, without metadata or an ICC profile. Failures are `PayloadTooLargeException` (413) and `UnsupportedMediaTypeException` (415). `CV.Logic.Tests` covers it and `GooglePictureUri`.
- `IProfilePictureStore` hides Azure Blob Storage (`BlobProfilePictureStore`, a singleton). Without a storage setting it answers 503 (`ServiceUnavailableException`), and a storage outage is 502 (`BadGatewayException`). A replaced or removed blob is deleted with `RemoveUnused` only after the database change is saved, and a failure there is logged, not thrown. A new blob is uploaded before the database points at it, and deleted again if that save fails.

## Profile creation

A Profile POST may accept an optional `CandidateId`:

- When supplied, find the existing Candidate by `Id`, verify `ProfileId` is `null`, attach the new Profile ID, and avoid creating a second Candidate.
- When omitted, reject with `ConflictException` (`409`) when the caller's identity already has a login (one CV per sign-in). For an unlinked Google identity, require `email_verified` and an email address in `Authentication:Google:AllowedSignUpEmails` (`GoogleAuthenticationOptions` through `IOptions`, compared case-insensitively), otherwise throw `ForbiddenException` (`403`). Then require a unique public URL segment, check it before creation, and create the Profile, the Candidate and its first `CandidateLogin` from the validated caller identity in one `SaveChanges`. Never accept the identity from the request body.
- Keep a unique database index on `PublicUrlSegment` as the final guard against concurrent duplicate creates. Candidate's `Id` remains generated by `BaseEntity`.
- Return the internal `CandidateId` and public `PublicUrlSegment` in the profile-admin response. The segment is immutable after creation.

The UI does not POST Candidate directly. Candidate currently exposes GET and DELETE only; later related resources can update Candidate with their generated IDs.

## Public profile lookup

The public frontend route has exactly one identifier segment: `/{publicUrlSegment}`. Do not introduce a nested frontend route such as `/{publicUrlSegment}/profile`.

Resolve the public route in two API reads:

1. Call `GET /api/Candidate/{publicUrlSegment}`. This looks up `Candidate.PublicUrlSegment` and returns `CandidateDto`, including internal `Id` and nullable `ProfileId`.
2. If `ProfileId` is non-null, call `GET /api/Profile/{profileId}` for the public profile content.

Do not add a duplicate `GetProfileByCandidateId` endpoint/service method. Candidate lookup resolves the Candidate ID; the existing profile read continues to take the Profile ID.

If a Candidate has no Profile, show an explicit not-yet-published state. If either lookup fails, surface the error rather than substituting a different candidate or hard-coded profile.

## Existing Profile service behavior

- `CreateProfile` and `UpdateProfile` reject a blank full name, missing translations, unsupported language codes, duplicate language codes, blank translation titles, and requests without the required Finnish (`fi`) translation. Only `fi` and `en` are supported.
- `CreateProfile` can attach to an existing Candidate using `CandidateId`, but rejects an unknown Candidate or one that already has a Profile. Without that key, the service creates the Candidate and Profile together.
- Public `GetProfile` reads one language (default `fi`). Language values are normalized to lowercase; an absent requested translation falls back to Finnish. Invalid language values are a `BadRequestException`.
- `GetProfileAdmin` returns all translations. `UpdateProfile` replaces the translation set: omitted languages are removed, new ones added, and existing ones updated with tracking timestamps.
- Profile/Candidate service lookups use `BadRequestException` for an empty Guid and `NotFoundException` for a missing row. Keep those rules in the service, not just route/model binding.

## Authorization boundary

Public profile and candidate reads are intended to be anonymous. The API accepts two bearer tokens behind the `Bearer` policy scheme, which picks the scheme from the token's unvalidated `iss` (`BearerSchemes.Select`): Entra access tokens (`Entra` scheme) and Google ID tokens whose audience is `Authentication:Google:ClientId` (`Google` scheme, registered only when the client ID is set). Controllers read the caller through `ICurrentUser`, which returns an `ExternalIdentity` and `IsCvAdmin`; never read claims such as `oid` directly. Profile create requires authentication and links the caller's identity as the first login. Profile update, delete, admin-read, and Candidate delete require authentication and are allowed only to a caller whose identity matches one of the Candidate's logins (`CandidateLoginQueryExtensions.ForIdentity`) or a caller with the global `CvAdmin` role; a non-owner gets `404`. `CvAdmin` comes only from Entra app roles: the Google scheme uses a role claim type that Google never issues. Admin-read updates the owner's `LastSignInAt`. The API must enforce this regardless of frontend affordances. Configure `AzureAd:TenantId`, `AzureAd:ApiClientId`, and `AzureAd:Audience` to match the tenant, API registration, and access token claims. Public URL segments are identifiers, not secrets; the admin Profile endpoint takes the internal Profile ID. Entra registration steps are kept out of the repository, which is public.
