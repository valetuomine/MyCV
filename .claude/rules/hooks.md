# Hooks and status line

Implementation notes for the hooks in `.claude/hooks/` and their registration in `.claude/settings.json`. `CLAUDE.md` (*Tools*) holds what each hook does for the user.

## Weekly usage budget

The status line (`.claude/hooks/usage-statusline.mjs`, `statusLine` in `.claude/settings.json`) shows the weekly usage, today's cumulative limit and the five-hour window usage with the time the window resets, e.g. `Viikko 38 % / raja 42 % · 5 h 12 % (nollautuu 14:30) · Konteksti 182k` (the last part is the context size, `context_window.total_input_tokens`); the time is left out when `resets_at` is missing or already past. It stores the weekly usage in the temp directory, and the `UserPromptSubmit` hook `.claude/hooks/usage-budget.mjs` reads it and shows a `systemMessage` warning once a day when usage nears the limit and once when it passes it. It never blocks a message.

Each weekday's share is set in `.claude/hooks/usage-budget.json` (default 14 % a day, warning margin 3 percentage points). The limit is cumulative from the week's start (`resets_at` minus 7 days), so an unused day moves its share to the following days. Both scripts share `usage-budget-core.mjs`, which takes the limit and the warning from the usage-band plugin's `core.mjs` (*Usage band plugin*).

The status line runs only in a local terminal Claude Code CLI session, and a missing file or field is skipped silently. The desktop app and the VS Code chat panel do not run it, so the hook has at most an old CLI snapshot to read there; the usage-band plugin draws the numbers and gives the warnings on those surfaces instead.

## Usage band plugin

`.claude/skills/usage-band/` is a Claude Code plugin (a mod: `.claude-plugin/plugin.json`, `hooks/hooks.json`, `hooks/register.tsx`). Claude Code loads a plugin from the project's skills folder by itself, as `usage-band@skills-dir`. It covers the surfaces that have no status line:

- **Row above the prompt** (`ui.render` on `AbovePrompt`): `Viikko 22 % / 14 % · 5 h 64 % (nollautuu 00:30) · Konteksti 92k / 200k (46 %)`, in Finnish like the status line, from the session's own usage (`session.measure`), with the same cumulative daily limit as the status line. The context part is measured against `stopTokens` (the limit where the work moves to a new chat), not against the model's context window that the app's own `context.percent` uses, so 100 % means the stop is reached. Parts that are not known are left out. It is not drawn on the `terminal` surface, where the status line already shows the numbers (the model hint bar is drawn there too).
- **Warnings** (`session.measure`, as toasts to the user only): the weekly budget warnings once a day (markers in `$.store`) and the context warning once a session, starting again after the context shrank (`$.state`). The plugin sends the model nothing, so the classic `PostToolUse` hook stays the only thing that tells Claude to stop.
- **Context stop** (`prompt.submit`): over `stopTokens` a message that does not start with `/` is dropped and `/handoff` runs once, through `$.command.run` from a timer (a `prompt.submit` hook cannot run a command itself, and a submitted `/handoff` text is refused). Commands, meta messages and any error let the message through.
- **Model hint bar** (`prompt.submit` and `ui.render` on `AbovePrompt`, all surfaces including the terminal): when the first message of a chat (not a `/` command) names `US-<id>`, `Task-<id>`, `User Story <id>` or `Task <id>`, a timer fetches the work item's description with `$.http.fetch` (the project URL from `.claude/azure-devops.json`, `Authorization: Basic` from `$.env.get('AZURE_DEVOPS_MCP')`, or the cloud environment's placeholder token that the proxy swaps) and `parseEstimate` reads its `Työmäärä` line. The bar shows e.g. `US-47 · M · Sonnet, medium` above the prompt for the rest of the chat. It never stops or changes the message and never switches the model; only the first message is looked at, a failed lookup is not retried, and with no work item, no `Työmäärä` line or any error the bar is left out. It replaced the `model-hint.mjs` hook, which stopped the first message, so a brief for a session started from another session may write `User Story <id>` again.
- **Never guard** (`tool.call`): for a Bash or PowerShell call it reads the command with `findGitOperations` (`core.mjs`: `git push`, `commit`, `add`/`stage`, also behind `cd`, `-C`, env assignments, `sudo`, `&&`/`;`/`|` chains and `sh -c`/`pwsh -Command`/`eval` strings) and returns `{ deny }` with a reason from `checkGitOperation` for: a push to any remote but `azure` (and `origin` on a local checkout, where it is Azure DevOps; in a cloud session `CLAUDE_CODE_REMOTE=true` makes `origin` the public GitHub mirror), a push to `main` (`main`, `HEAD:main`, `refs/heads/main`, `:main`, `--delete main`, `--all`, `--mirror`, wildcard refspecs, or no refspec while `main` is checked out), a commit while `main` is checked out, and `git add`/`commit` naming `.env.local` or `.mcp.json`. The branch is read from the directory's `.git` (`HEAD`, or the worktree's `gitdir:` file); unknown means only what the command itself shows is checked. Feature branch pushes to `azure`/`origin` pass. Any error lets the call through.
  - **Command forms** (`splitCommands` and `findGitOperations` in `core.mjs`): a shell string is read again when the command is a shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `pwsh`, `powershell`, `cmd`) with `-c`, `-xc`, `-Command`, `/c` or `/k`, or is `eval`, `iex` or `Invoke-Expression`; several words after the flag are joined and quoted again, and `pwsh`/`powershell`/`iex` read it as PowerShell, the rest as Bash. `grep -c "git push"` is not a command string. Prefixes `env` (with `-u`, `-C`), `sudo`, `timeout`, `xargs`, `wsl`, `nice` and their options are skipped. PowerShell here-strings (`@'...'@`), Bash heredocs, `\"` in Bash quotes, `''`, `""` and the backtick escape and line continuations are read as the shell reads them, so text in a commit message body is not taken for a command; a body that a shell or `iex` reads (`bash <<EOF`, `cat <<EOF | bash`, `iex @"..."@`) is read as a command line of its own; so is the here-string `bash <<< "..."` (a here-string piped to a shell through another command, `cat <<< "..." | bash`, is not read).
  - **Branch switch:** `git switch` and `git checkout` in the same command decide the branch of the later `commit` and `push` in the same directory (`switchedTo`), so `git switch -c feat/x && git commit` on `main` passes and `git checkout main && git commit` is denied. Only `&&` counts, both between the switch and the commit and in front of the switch itself: after `;`, `||`, `|` or a newline the switch may have failed or been skipped (`true || git switch -c f && git commit`), so both the switched and the checked-out branch are checked (`switchUncertain`). `git checkout <name>` is a switch only for `main` (it may restore a file); `.`, `--`, `-p`, `--ours`, `--theirs` and `checkout <ref> <file>` are not, `-t` strips the remote name, and a target that is not known (`-`) is checked together with the checked-out branch. Callers skip reading the branch when the switch is certain (`needsBranch`).
  - **Details:** `cd`, `pushd`, `Set-Location` and `sl` skip option words and read `-Path`/`-LiteralPath`; a Git Bash path `/c/repo` becomes `C:/repo` when the working directory is a Windows path; `@` means `HEAD` in a refspec, `refs/heads/` and `heads/` are removed and `main` is compared in lower case; the values of `-m`, `-F`, `-C`, `-c`, `-t`, `-am`, `--message`, `--file`, `--author`, `--date`, `--fixup` and `--squash` are not file names; a remote URL is judged by its host (`isAzureUrl`: `dev.azure.com`, `visualstudio.com` and their subdomains), and the classic hook also checks the push URL of `azure`. Not covered, the limits of a text parser: variables, aliases, `Start-Process git`, and merge, cherry-pick or revert on `main`.
- **Never guard, classic hook:** `.claude/hooks/never-guard.mjs` (`PreToolUse`, matcher `Bash|PowerShell`) does the same with the same `core.mjs` functions, for `claude -p`, cloud sessions and surfaces without the plugin; it also denies a commit when `.env.local` or `.mcp.json` is already staged. In the desktop app both run; a deny from either blocks the call. General risk-command protection (`rm -rf`, force push, preview with proceed/cancel, the Blast Radius mode) is left out of this story.
- **Model switch button** (`ui.render` on `AbovePrompt`): a plain `Vaihda malli` Button beside the model hint bar runs `$.command.run({ command: 'model' })`, the `/model` picker. A test presses the button and checks that `command.run` gets `model`; whether the picker then opens in a live session is not verified.
- **Session toolbar buttons** (`session.start` and `ui.render` on `AbovePrompt`): two more plain Buttons, `Siivoa haarat` and `Tarkista origin/main`, sit in the same row, also when there is no model hint. At `session.start` the plugin probes once (`probeToolbar`, without any git call): they are drawn only when `CLAUDE_CODE_REMOTE` is not `true` (a cloud session, where `origin` is the public mirror) and `$.fs` finds a `.git` folder or file in the session folder or a parent (`insideGitFolder`), so their visibility does not depend on `$.process.run`, which is documented as CLI only. `Siivoa haarat` runs `$.command.run({ command: 'clean-branches' })`; if that rejects, it submits the prompt `Aja /clean-branches-skilli.` through `$.prompt.submit`, and a toast asks the user to type the command when that fails too. Either way the skill's own approval table still has to be answered before anything is deleted, and the button itself runs no git. `Tarkista origin/main` runs `git fetch --quiet --prune origin`, `git rev-list --left-right --count HEAD...origin/main` and `git branch --show-current` (each with a 20 s limit and `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, like the fetch of `worktree-sync.mjs`; it fetches and counts the same way but is its own code; only remote-tracking branches change, never HEAD, the index or the working tree), first shows `Haetaan origin/mainia...` and then `syncStatus` (`core.mjs`) as a toast: behind (fast-forward possible), behind with own commits, only own commits, or up to date; a failed fetch (or a refused `$.process.run`) gives a failure toast, and a second press while a check runs does nothing. Tests press each button and check the argv list and the toast (`claude plugin test`). Not verified: whether `command.run` starts a skill in a live desktop session, and whether `$.process.run` is allowed there; open the app in a new session to check, and if the skill needs the prompt route, the fallback already covers it.
- **Cold session warning** (`turn.start`, `turn.complete` and `prompt.submit`): the main chain's `turn.start` and `turn.complete` (not a subagent's) store the time and whether a turn is running in `$.state` (`lastTurn`). When a message that does not start with `/` is let through and more than `coldAfterSeconds` (3600, set in `.claude/hooks/cold-session.json`; a missing file or bad value falls back to one hour) have passed since the last turn started or ended, a toast tells the user that the prompt cache has probably expired, so the whole context (its size is shown when known) is read again without the cache, and suggests either continuing as is or starting a new chat with `/handoff`. The prompt cache lifetime depends on the plan and settings (five minutes by default, an hour in the extended mode), so the limit is a setting and the text says `todennäköisesti`. The message always goes through unchanged. Nothing is shown while a turn is running (a message that steers a long turn), for a message that the context stop drops (it gets only the stop notice), in a session that has stored no turn and whose transcript does not exist yet or was written within the limit (a brand-new session), or when no surface draws the session; because the next turn restarts the clock, a let-through message warns once. A session with no stored turn time, such as one that Claude Code resumed after a restart, uses the time its transcript file was last written instead (`$.session.info().transcriptPath`, `$.fs.stat`), so any such session whose transcript is older than the limit warns on its first message; the stored turn time wins once a turn has run, and when neither is known nothing is shown. Unlike the budget and context warnings it runs on every surface including the terminal, because no classic hook or status line part gives it, so it is never shown twice. `coldSessionWarning` and `parseColdConfig` live in `core.mjs`, and the tests cover them. As with the other limits, a worktree session reads the main checkout's `cold-session.json`.
- **Testing the cold session warning by hand:** the plugin loads from the main checkout's `.claude/skills/usage-band/`, so a change shows up in a new session only after that checkout has the branch or `main` with it (a feature branch's worktree does not count, and the desktop app does not start from the worktree's copy). To try an unmerged change, start `claude --plugin-dir .claude/skills/usage-band` in a terminal from the worktree; to try a merged one, update the main checkout. Set `coldAfterSeconds` to `30` in the `cold-session.json` that the loaded plugin reads, send a message, wait over 30 seconds without a turn running and send another: the toast appears with that message. To try the resume path, send one message, quit, wait over the limit, resume the session with `claude --resume` and send a message. `claude plugin test .claude/skills/usage-band` covers the same cases without waiting.
- **Classic hooks run too:** the desktop app also runs the classic `context-budget.mjs` and `usage-budget.mjs`. Over `warnTokens` the user can get both the plugin's toast and the classic hook's `systemMessage`, if the app shows the latter. `usage-budget.mjs` reads the snapshot that only the CLI status line writes, so in the app it can warn from an old CLI reading, or not at all. The plugin's toast is the one to trust there.
- **Worktree sessions:** the desktop app can run a session in a worktree under `.claude/worktrees/`. The plugin then loads from the main checkout and reads that checkout's settings files, while the classic hooks read the worktree's copies. Change the limits in both when testing.

The usage row is left out only on the `terminal` surface itself (`e.surface`), so a Remote Control session still draws it on the phone. The warnings and the context stop are off whenever a terminal draws the session at all (`$.session.surfaces()` includes `terminal`, as it does under Remote Control), and also while no surface draws it, so the CLI keeps the status line and the settings hooks without anything shown twice. The settings stay in `.claude/hooks/usage-budget.json` and `context-budget.json`, which the plugin reads from `$.plugin.root + '/../../hooks/'`. The calculations live in `hooks/core.mjs` (plain JS with no Node imports, so the plugin can load it), and the scripts in `.claude/hooks/` import it, so both give the same limits and texts. The plugin's tests run with `claude plugin test .claude/skills/usage-band`, its manifest and module are checked with `claude plugin validate .claude/skills/usage-band`, and `core.mjs` (with `parseEstimate`) is linted with the hooks (`lint:hooks`). The tracked `tsconfig.json` extends `.claude-plugin/types/tsconfig.json`, which holds the plugin API's types (`claude-code`, `claude-code/testing`) and the JSX settings. That folder is git-ignored, and Claude Code writes it only when it hot-reloads the plugin, not when it loads it from the skills folder. Until it exists, the editor reports `Cannot find module 'claude-code'` and `tsc -p .claude/skills/usage-band` fails. Write it once per clone, and again after a Claude Code update, by starting an interactive session with `claude --plugin-dir .claude/skills/usage-band` from the repository root and closing it; `claude -p` does not write it. Then type-check with `npx --prefix src/Frontend tsc -p .claude/skills/usage-band`.

## Context budget

`.claude/hooks/context-budget.mjs` (`UserPromptSubmit` and `PostToolUse`, registered in `.claude/settings.json`) reads the context size of the latest main-chain assistant message from the end of the transcript, so it works in the VS Code chat panel too. Limits are in `.claude/hooks/context-budget.json` (`warnTokens` 150000, `stopTokens` 200000, `repeatEveryTokens` 25000; a missing file or bad value falls back to the default).

- Over `warnTokens` the user and Claude get one warning per session. The notices start again when the context has shrunk below the limit and grows back, as after `/compact`. A `warnTokens` at or above `stopTokens` falls back to the defaults.
- Over `stopTokens` a `UserPromptSubmit` message is blocked unless it starts with `/` (`/handoff`, `/compact`, `/clear` pass), and `PostToolUse` tells Claude to stop at the next safe point, run `/handoff` and end the turn, repeated every `repeatEveryTokens`.
- `/handoff` writes the work state as a `Handoff` comment on the work item and prints a start message for a new chat.
- Subagent context is not limited (tool calls with an `agent_id` are ignored), and the hook does nothing on any failure.
- The auto-compact threshold is left alone: a new chat with a handoff loses less detail than a compact.

## Worktree sync at session start

`.claude/hooks/session-start.mjs` is the one `SessionStart` entry in `.claude/settings.json` for the sync and the graph (matcher `startup|resume`, timeout 95 s, not `async`, because the output must reach the session). Claude Code starts the hooks of one event in parallel, so the order in `settings.json` would not order them. The runner therefore runs `worktree-sync.mjs` (30 s limit) and then `graphify-session.mjs` (60 s limit, unchanged) one after the other, because the graph compares its `built_at_commit` with `HEAD` and must not read a tree that is still being fetched or merged. It prints the two additional contexts as one JSON; a step that fails or prints nothing is skipped silently. `clean-playwright-mcp.mjs` stays its own `async` hook.

`.claude/hooks/worktree-sync.mjs` runs `git fetch --prune origin` (15 s limit, 25 s budget for the whole hook, git never prompts for credentials: `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`) and counts the commits `HEAD` is behind `origin/main`. It prints nothing when `HEAD` is not behind in a worktree and no branch has a gone upstream, nothing on any failure (no network, no `origin/main`) and nothing in a cloud session (`CLAUDE_CODE_REMOTE` is `true`), and always exits with 0.

- **Worktree** (git-dir differs from git-common-dir): with a clean working tree and `HEAD` an ancestor of `origin/main` (`git merge-base --is-ancestor`), it runs `git merge --ff-only origin/main` (10 s limit, started only when at least that much of the budget is left) and reports the update, with a reminder that `CLAUDE.md`, the rules and the skills were loaded before it. Otherwise it reports how far behind the branch is and why it was not updated: uncommitted changes, commits of its own in the branch, too little time left, or a failed merge. A squash-merged branch looks like a branch with commits of its own and is only reported, with the hint to start a new branch from `origin/main`.
- **Main checkout**: never switched, updated or merged. It reports only when the branch is not `main` (even when not behind) or is behind `origin/main`, and reminds that the usage-band plugin is loaded from this checkout.
- **Branch cleanup hint**: after the sync note, it counts the local branches (not `main`, not the current one) whose upstream is `gone` (`git for-each-ref`, `%(upstream:track)`) and the linked worktrees of `git worktree list --porcelain` (the first block, the main checkout, is left out) that are on such a branch, and adds one line saying so. It is a local hint only: no Azure DevOps call, nothing is deleted, and a branch without an upstream is never counted. It fires only when the source branch is deleted at pull request completion. The `/clean-branches` skill (`.claude/skills/clean-branches/SKILL.md`) does the real check and the deletion, after the user agrees.
- Output is a short `additionalContext` like the code graph hook's. `reset --hard`, `stash`, `--force` and `checkout` are not used. Try it by hand with `node .claude/hooks/worktree-sync.mjs` in a worktree and in the main checkout.

## Main checkout sync (scheduled)

`.claude/hooks/sync-main-checkout.mjs` is not a Claude Code hook but a script for a Windows scheduled task. It keeps the main checkout (the folder that holds the real `.git`) on `main` and up to date with `origin/main`, because the usage-band plugin and the toolbar buttons load from that checkout. The worktree sync hook still never changes the main checkout, and sessions never switch its branch.

**Why the checkout was detached:** the main checkout's reflog showed `checkout: moving from claude/us-206-... to origin/main` (2026-11-25), so it had been on a desktop session's branch and then detached at `origin/main`. `.claude/skills/clean-branches/SKILL.md` says archiving a session detaches the worktree's `HEAD` at the branch tip, but the reflog does not say whether archiving or a command run by hand made that move, so the cause is not confirmed. `main` is also checked out in another worktree, so the checkout could not switch to it by hand either.

**What it does:** it fetches `origin` (30 s limit, no credential prompts) and updates the checkout only when nothing can be lost: a clean working tree, no merge, rebase, cherry-pick, revert or bisect in progress, and `HEAD` either on `main` or detached at a commit that `origin/main` contains.

- `main` behind: `git merge --ff-only origin/main`.
- Detached `HEAD`: when no other worktree has `main`, `git switch main` and the fast-forward (only if `main` itself has no commits that `origin/main` lacks); when another worktree has `main`, it stays detached and fast-forwards the detached `HEAD`. A stale worktree record (folder deleted, record still listed as `prunable`) counts as a worktree on `main`, because git then refuses the switch; the log line names it, and `git worktree prune` or `/clean-branches` clears it. No commit is lost either way.
- `main` already at `origin/main`: nothing changes.
- Otherwise (another branch, commits of its own, a dirty working tree, no network, a linked worktree as the folder) it changes nothing and logs the reason. It never uses `reset --hard`, `stash`, `checkout --force`, `--force` or a push, and always exits with 0.

**Log:** one line per run in `%LOCALAPPDATA%\MyCV\sync-main-checkout.log` (the `SYNC_MAIN_LOG` environment variable overrides the path), at most 100 lines. The optional first argument is the repository folder; the default is the one that holds the script.

**Schedule it once (a local, persistent setting, so run it only after deciding to):** replace `<main checkout>` with the path of the main checkout, and run in PowerShell:

```powershell
$node = (Get-Command node).Source
$script = '<main checkout>\.claude\hooks\sync-main-checkout.mjs'
$action = New-ScheduledTaskAction -Execute 'pwsh' -Argument "-NoProfile -WindowStyle Hidden -Command & '$node' '$script'" -WorkingDirectory '<main checkout>'
$triggers = @(
  (New-ScheduledTaskTrigger -Once -At (Get-Date) -RepetitionInterval (New-TimeSpan -Minutes 15)),
  (New-ScheduledTaskTrigger -AtLogOn)
)
$settings = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries -StartWhenAvailable -MultipleInstances IgnoreNew
Register-ScheduledTask -TaskName 'MyCV sync main checkout' -Action $action -Trigger $triggers -Settings $settings
```

The settings let it run on battery power, make up a run that was missed while the machine was off, and skip a run while the previous one is still going. `$node` is the full path of `node`, because a scheduled task may not have the same `PATH` as a terminal. `pwsh` with `-WindowStyle Hidden` is there because a console program run directly (`node`) opens a visible window on every run; even so, a window may flash for a moment. The command has not been run as a scheduled task here, so check the log after the first run.

Remove it with `Unregister-ScheduledTask -TaskName 'MyCV sync main checkout' -Confirm:$false`. The script file is read from the main checkout, so the first run uses whatever version that checkout has; update the checkout once by hand after this change is merged.

## Code graph at session start

`.claude/hooks/graphify-session.mjs` (`SessionStart`, run by `session-start.mjs` after the worktree sync, 60 s limit) gives Claude the code graph at the start of every session. It looks for `graphify-out/graph.json` in the project folder, and in a worktree session (`git rev-parse --git-common-dir` points outside the project folder) it copies `graph.json` and `manifest.json` from the main checkout when the worktree has none. It compares `built_at_commit` with `HEAD` and runs `python -m graphify update .` (never `--force`) when they differ; `manifest.json` holds only relative paths and the build state is not copied, so the update rebuilds it for the worktree, and the main checkout's graph is never modified from a worktree. A failed update does not stop the session: the summary says so, and in a worktree it adds `--graph <main checkout's graph.json>`. It then prints `additionalContext`: the graph's commit and `HEAD`, the file age, the five most connected nodes (`god-nodes`) and the `query`, `explain` and `affected` commands, about 150 tokens in all. A missing graph or graphify package (a cloud session, a fresh clone) and any other failure print nothing and exit with 0, and the hook runs no LLM and writes only into the git-ignored `graphify-out/`. Run it by hand with `node .claude/hooks/graphify-session.mjs` in the main checkout and in a worktree. The pull request step that refreshes the graph stays as it is (*Code graph* in `references/checks.md` of `/create-pull-request`).

## Playwright folder cleanup

`.claude/hooks/clean-playwright-mcp.mjs` (`SessionStart`, matcher `startup|resume`, `async` so it never delays the session start) deletes the files in the git-ignored `.playwright-mcp/` folder whose modification time is older than `retentionDays` (14 by default, set in `.claude/hooks/clean-playwright-mcp.json`; a missing file or bad value falls back to the default), then the folders left empty. Loose files directly in the root, which `@playwright/mcp` names and writes itself (`console-*.log`, `page-*.yml`), are deleted at the first session start after they are older than `looseFileRetentionHours` (1 by default, same file and same fallback; the hour protects the running check of a parallel chat), while files in the ticket folders keep `retentionDays`. With `--collect <US-id|Task-id> --since <ISO time>` the script instead moves the loose root files whose names start with `console-` or `page-` (what `@playwright/mcp` names itself, so a parallel chat's own files and files saved by hand stay) and that were modified at or after that time into `.playwright-mcp/<id>/` (created if needed), and prints `Moved <n> files to <id>`, with `, skipped <m>` when a file could not be moved (for example one that the browser still holds open) or the ticket folder already holds a file of that name. A missing `.playwright-mcp/` gives `Moved 0 files`. The id must be `US-<n>` or `Task-<n>`, otherwise it moves nothing and exits with 1, as it does when collecting fails; it skips subfolders and symbolic links and never overwrites an existing file. The browser subagent runs it at the end of every check (*Browser subagent* in `references/checks.md` of `/create-pull-request`). Retention is by age and not by work item state, because the state would need an Azure DevOps call. It never follows symbolic links, never touches anything outside `.playwright-mcp/`, in the cleanup mode prints nothing (except with `--report`) and does nothing on any failure. The scripts in `.claude/hooks/` are linted with the frontend's Sonar rules (`src/Frontend/eslint.hooks.config.js`, part of `npm --prefix src/Frontend run lint` as `lint:hooks`), and a hook change runs the frontend checks in the pipeline. Run it by hand with `node .claude/hooks/clean-playwright-mcp.mjs --report` to see how many files it deleted. Browser checks save their files in `.playwright-mcp/US-<id>/` or `.playwright-mcp/Task-<id>/` (*Screenshots* in `references/checks.md` of `/create-pull-request`).
